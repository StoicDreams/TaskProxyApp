- PDF

- WebUI Markdown (copies the raw page content from the file)

## Action Buttons

Generally action buttons should be disabled if the actions they perform depend on something that hasn't been added or in the case of Save buttons are saving something that would have no effect - saving a page wouldn't change the file because no changes have been made to the page since it was opened.

Another example is in the page section editor. Currently the Revert button is always active. If the section being edited doesn't have any changes then that button should be disabled to indicate no changes have been made.

This makes it easier for users to understand/remember when they've made changes to something and haven't saved it yet or more things are required before they can perform an action.

## Git Controller UX

The Git Controller needs to remember which tab is active on a per-project basis. The less users have to reclick through pages/sections when switching back and forth between projects the better UX we are providing.

## Pages pending Changes

When a user is on a page making changes to sections it can be very easy to forget to save the changes they are making. I would like to address this with 2 features.
1. Retain pending changes in cache that will be retained even through an app restart.
2. When they try to navigate to a different page and the current page has pending changes block the page change and present a dialog letting them know that they have unsaved changes. Provide them with the option of cancelling the navigation, saving and continuing the navigation, or leaving the changes unsaved and continue the navigation.

Since change should now persist in a cache I want a way to clear them for the page. When changes are pending in a page add a Revert button next to the Save buttons to revert all pending page changes. They should still also be able to revert cached sections by using the revert button in the section editor.

## Limits Per Provider

Currently there is a Limits Per Provider to set limits for all providers. This doesn't make sense to have since even models within a single **provider** can have various limits from one another.
This needs to be removed and instead allow setting limits per specific model. Ideally each model limits will default to "our suggestion" on a per model basis based on that models documented limits - not defaulting to the max, but an actual recommended limit that would be good for that specific model.
